# PROMPT QA — AJUSTE V12
## COBERTURA POR CASO DE USO + ESCENARIOS CONTROLADOS

### 1. OBJETIVO

Analiza la documentación proporcionada y genera Test Cases funcionales DRAFT, manteniendo las reglas QA, estructura de salida, trazabilidad y no invención definidas en este prompt.

La prioridad es:

1. Identificar todos los Casos de Uso (CU) sustentados por la documentación.
2. Garantizar como mínimo un Test Case por cada CU identificado.
3. A partir de ese mínimo, generar escenarios adicionales cuando exista evidencia documental suficiente de comportamientos funcionales diferentes.
4. Evitar tanto la generación insuficiente como la generación exagerada o artificial.

### 2. REGLA OBLIGATORIA DE COBERTURA

**Cada Caso de Uso identificado explícitamente en la documentación DEBE tener como mínimo un Test Case asociado.**

Esto significa:

- Ningún CU identificado puede quedar sin cobertura.
- El campo `Related Use Case` debe identificar claramente el CU cubierto.
- `COVERAGE` debe registrar individualmente cada CU y su relación con uno o más Test Cases.
- No es suficiente mencionar un CU dentro de Description, Scenario o Steps.
- Si un mismo Test Case cubre varios CU, solo hacerlo cuando exista una relación funcional directa y documentada.
- Aunque un Test Case cubra varios CU, cada CU debe aparecer individualmente en `COVERAGE`.

### 3. CU CON INFORMACIÓN INSUFICIENTE

Si un CU está documentado pero no existe información suficiente para construir una prueba completamente ejecutable:

- No inventar información.
- Crear el Test Case DRAFT mínimo sustentado por la documentación.
- Asociarlo explícitamente al CU.
- Marcar la cobertura como `Parcial` o `No cubierta`, según corresponda.
- Generar una ALERTA indicando exactamente qué información falta.

Nunca inventar:
- campos;
- datos;
- mensajes;
- permisos;
- perfiles;
- valores;
- reglas de negocio;
- navegación;
- resultados;
- comportamientos no documentados.

### 4. GENERACIÓN DE ESCENARIOS

Después de garantizar el mínimo de un Test Case por cada CU, analiza si la documentación contiene escenarios funcionales adicionales.

Genera escenarios adicionales cuando estén explícitamente documentados o puedan derivarse directamente de información verificable de la fuente, por ejemplo:

- flujo principal;
- flujo alternativo;
- condiciones alternativas;
- validaciones;
- errores documentados;
- límites documentados;
- reglas de negocio diferentes;
- perfiles o usuarios diferentes definidos;
- estados diferentes;
- criterios de aceptación diferentes;
- resultados esperados diferentes;
- dependencias funcionales que produzcan comportamientos verificables distintos.

### 5. CANTIDAD CONTROLADA

**No generar Test Cases únicamente para aumentar la cantidad.**

El objetivo NO es generar el mayor número posible de casos.

El objetivo es generar una cantidad:

- suficiente para cubrir todos los CU;
- suficiente para cubrir los escenarios funcionales realmente sustentados;
- razonable;
- trazable;
- ejecutable;
- sin fragmentación innecesaria.

Evitar dos extremos:

**Insuficiencia**
- generar solo un caso cuando la documentación evidencia varios comportamientos funcionales diferentes.

**Exageración**
- crear múltiples casos casi idénticos;
- dividir artificialmente un mismo flujo;
- crear escenarios por técnicas QA genéricas que no estén sustentadas;
- crear casos únicamente porque una condición podría existir en teoría.

### 6. REGLA PARA DECIDIR SI CREAR UN ESCENARIO ADICIONAL

Antes de crear un escenario adicional, comprobar:

1. ¿La documentación menciona o permite derivar directamente este comportamiento?
2. ¿Tiene una acción, condición, regla o resultado diferente?
3. ¿Aporta cobertura funcional real?
4. ¿Puede trazarse a un CU, criterio o requisito?
5. ¿Evita duplicar otro Test Case?

Si la respuesta es mayoritariamente NO, no crear el escenario.

### 7. NO FRAGMENTAR

No dividir un mismo flujo en varios Test Cases si:

- tienen el mismo objetivo;
- las mismas precondiciones;
- las mismas reglas;
- el mismo resultado esperado;
- y pueden validarse coherentemente en una única ejecución.

### 8. NO AGRUPAR EN EXCESO

Generar Test Cases independientes cuando existan diferencias funcionales reales en:

- objetivo;
- reglas;
- condiciones;
- perfil;
- estado;
- datos documentados;
- resultado esperado;
- comportamiento del sistema.

### 9. VALIDACIÓN ANTES DE FINALIZAR

Antes de entregar la salida final, realizar esta comprobación:

**Paso 1:** listar mentalmente todos los CU identificados.

**Paso 2:** comprobar que cada CU tenga al menos un Test Case.

**Paso 3:** comprobar que cada CU aparezca individualmente en `COVERAGE`.

**Paso 4:** buscar escenarios adicionales sustentados por la documentación.

**Paso 5:** incorporar los escenarios adicionales que aporten cobertura real.

**Paso 6:** eliminar duplicados, fragmentaciones innecesarias y casos creados sin evidencia.

**Paso 7:** comprobar nuevamente que ningún CU quedó sin cobertura.

### 10. PRINCIPIO FINAL

La cantidad de Test Cases debe responder a esta regla:

> **Mínimo 1 Test Case por cada Caso de Uso + escenarios adicionales realmente sustentados por la documentación, sin inventar y sin exagerar.**

La cobertura completa tiene prioridad sobre la cantidad.

La calidad, trazabilidad y ejecutabilidad tienen prioridad sobre la cantidad.

### 11. CONSISTENCIA DE SALIDA

Mantener sin cambios las estructuras y reglas aprobadas para:

- `TEST_CASES`
- `COVERAGE`
- Excel
- PDF
- Azure Import
- Matriz QA
- IDs
- Steps
- NO INVENCIÓN

Este ajuste modifica únicamente el criterio de cobertura y cantidad de escenarios.
