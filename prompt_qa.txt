# PROMPT QA — COBERTURA POR CASO DE USO

## REGLA OBLIGATORIA DE COBERTURA

Cada Caso de Uso (CU) identificado en la documentación DEBE tener como mínimo un Caso de Prueba (CP) propio.

### Regla estricta

**1 Test Case = 1 Caso de Uso.**

No crear relaciones entre funcionalidades diferentes.

Por lo tanto:

- Cada CP debe estar asociado a un único CU.
- `Related Use Case` debe contener un único CU.
- Cada relación registrada en `COVERAGE` debe relacionar un CP con un único CU.
- No colocar varios CU dentro del mismo Test Case.
- No agrupar CU diferentes aunque pertenezcan a la misma HU, módulo, pantalla, proceso o flujo.
- No considerar que mencionar varios CU dentro de Description o Steps equivale a cubrirlos.

### Cobertura mínima

Antes de finalizar la generación:

1. Identificar todos los CU sustentados por la documentación.
2. Generar como mínimo un CP independiente para cada CU.
3. Verificar que ningún CU quede sin CP.
4. Verificar que ningún CP esté relacionado con más de un CU.

La cantidad mínima de CP debe corresponder al número de CU identificados.

## ESCENARIOS ADICIONALES

Después de garantizar el mínimo de un CP por cada CU, generar CP adicionales únicamente cuando la documentación sustente un comportamiento funcional diferente.

Se pueden generar escenarios adicionales cuando existan, por ejemplo:

- flujo principal y flujo alternativo documentados;
- validaciones diferentes;
- reglas de negocio diferentes;
- condiciones diferentes;
- errores documentados;
- límites documentados;
- estados diferentes;
- perfiles o roles diferentes explícitamente definidos;
- criterios de aceptación diferentes;
- resultados esperados diferentes;
- comportamientos funcionales distintos claramente sustentados.

Los CP adicionales de un mismo CU siguen respetando:

**1 CP = 1 CU.**

## NO EXAGERAR

No generar casos para aumentar artificialmente la cantidad.

No crear casos casi idénticos.

No dividir artificialmente un mismo flujo.

No utilizar técnicas QA genéricas para inventar escenarios que no estén sustentados por la documentación.

El objetivo es:

**Cobertura completa + escenarios suficientes + cantidad razonable.**

No es objetivo generar la mayor cantidad posible de CP.

## NO AGRUPAR FUNCIONALIDADES

Si existen:

- CU-001 Crear funcionalidad
- CU-002 Validar funcionalidad
- CU-003 Consultar funcionalidad

la salida mínima debe ser:

- CP-001 → CU-001
- CP-002 → CU-002
- CP-003 → CU-003

Nunca:

- CP-001 → CU-001 + CU-002
- CP-002 → CU-003

Aunque las funcionalidades estén relacionadas funcionalmente.

## INFORMACIÓN INSUFICIENTE

Si un CU está documentado pero no existe suficiente información:

- crear el CP DRAFT mínimo sustentado;
- asociarlo exclusivamente a ese CU;
- no inventar pasos, datos, mensajes, permisos, campos o resultados;
- marcar la cobertura como Parcial o No cubierta;
- generar ALERTA indicando qué información falta.

## VALIDACIÓN FINAL

Antes de entregar la salida:

- Todos los CU identificados tienen al menos un CP.
- Cada CP tiene exactamente un CU.
- Cada fila de COVERAGE tiene exactamente un CU.
- No existen CP relacionados con varios CU.
- Los escenarios adicionales tienen sustento documental.
- No existen duplicados ni casos creados únicamente para aumentar cantidad.

Reglas conceptuales:

`Para cada CU: cantidad de CP asociados >= 1`

`Para cada CP: cantidad de CU asociados = 1`

## CONSERVAR

No modificar:

- estructura TEST_CASES;
- estructura COVERAGE;
- ALERTS;
- IDs;
- Steps;
- Excel;
- PDF;
- Azure Import;
- Matriz QA;
- reglas de NO INVENCIÓN.

Este ajuste modifica únicamente el criterio de cobertura y generación de escenarios.
