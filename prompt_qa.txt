# PROMPT QA — V13
## COBERTURA OBLIGATORIA POR CASO DE USO — SIN RELACIONES ENTRE FUNCIONALIDADES

### OBJETIVO

Analiza exclusivamente la documentación proporcionada y genera Test Cases funcionales DRAFT con trazabilidad completa, sin inventar información.

La regla de cobertura es estricta:

**CADA CASO DE USO IDENTIFICADO DEBE TENER COMO MÍNIMO UN CASO DE PRUEBA PROPIO.**

### 1. REGLA OBLIGATORIA: UN CU POR CP

Para cada Caso de Uso (CU) identificado en la documentación:

- Generar como mínimo un Test Case.
- Ese Test Case debe estar asociado a UN SOLO Caso de Uso.
- El campo `Related Use Case` debe contener un único CU.
- La fila correspondiente de `COVERAGE` debe contener un único CU.
- No combinar varios CU en un mismo Test Case.
- No crear relaciones entre funcionalidades diferentes.

### 2. PROHIBICIÓN DE AGRUPAR FUNCIONALIDADES

NO está permitido:

- Crear un Test Case que cubra simultáneamente CU-001 + CU-002.
- Colocar varios CU dentro de `Related Use Case`.
- Crear una fila de `COVERAGE` que relacione un Test Case con varios CU.
- Agrupar funcionalidades diferentes solo porque pertenezcan a la misma HU, módulo, pantalla, proceso o flujo general.
- Considerar que una mención de varios CU dentro de Description, Scenario o Steps equivale a cobertura independiente.

**Regla:** 1 Test Case → 1 Caso de Uso.

Si dos CU tienen pasos parecidos, reglas parecidas o aparecen en la misma pantalla, siguen siendo casos independientes si están identificados como CU diferentes.

### 3. COBERTURA MÍNIMA

Antes de generar escenarios adicionales:

1. Identificar todos los CU sustentados por la fuente.
2. Crear mínimo un CP independiente para cada CU.
3. Verificar que cada CU tenga su CP propio.
4. Verificar que ningún CP tenga más de un CU asociado.

La cantidad mínima de CP debe ser igual al número de CU identificados, salvo que la documentación no permita identificar un CU con certeza. En ese caso, no inventar: registrar ALERTA y usar únicamente información sustentada.

### 4. ESCENARIOS ADICIONALES, SIN EXAGERAR

Después de garantizar un CP independiente por cada CU, evaluar si ese CU tiene escenarios funcionales adicionales sustentados por la documentación.

Crear CP adicionales para el mismo CU únicamente cuando exista un comportamiento funcional realmente diferente, por ejemplo:

- flujo principal y flujo alternativo documentados;
- validación diferente;
- regla de negocio diferente;
- condición diferente;
- error documentado;
- límite documentado;
- estado diferente;
- perfil/rol diferente explícitamente definido;
- criterio de aceptación diferente;
- resultado esperado diferente;
- comportamiento funcional distinto claramente sustentado.

### 5. CONTROL DE CANTIDAD

No crear casos adicionales solo para aumentar la cantidad.

No usar listas genéricas de técnicas QA para fabricar escenarios que no estén sustentados.

No duplicar casos.

No fragmentar un mismo escenario en varios CP si el objetivo, condición, comportamiento y resultado son esencialmente los mismos.

La regla es:

**Mínimo 1 CP independiente por CU + CP adicionales solo cuando aporten cobertura funcional real y estén sustentados.**

### 6. EJEMPLO

Si la documentación identifica:

- CU-101 Crear pestaña Ajuste de Tasas
- CU-102 Validar rangos
- CU-103 Calcular prima

La salida mínima debe ser:

- CP-001 → CU-101
- CP-002 → CU-102
- CP-003 → CU-103

NO:

- CP-001 → CU-101 + CU-102
- CP-002 → CU-103

Si CU-102 tiene además un escenario de error documentado:

- CP-002 → CU-102 — flujo principal
- CP-004 → CU-102 — error documentado

Sigue siendo 1 CU por CP.

### 7. INFORMACIÓN INSUFICIENTE

Si un CU existe pero la documentación no permite definir completamente el flujo:

- Crear el CP mínimo DRAFT asociado exclusivamente a ese CU.
- No inventar Steps, datos, mensajes, permisos, campos ni resultados.
- Marcar cobertura como `Parcial` o `No cubierta`.
- Crear ALERTA indicando qué información falta.

### 8. NO INVENCIÓN

Nunca inventar:

- datos;
- valores;
- mensajes;
- usuarios;
- perfiles;
- permisos;
- campos;
- navegación;
- reglas;
- respuestas del sistema;
- resultados no documentados.

### 9. VALIDACIÓN OBLIGATORIA ANTES DE ENTREGAR

Verificar:

- Todos los CU identificados tienen al menos un CP.
- Cada CP tiene exactamente un CU en `Related Use Case`.
- Cada fila de `COVERAGE` relaciona un CP con exactamente un CU.
- No existen relaciones CP → varios CU.
- No existen funcionalidades agrupadas artificialmente.
- Los CP adicionales tienen sustento documental.
- No hay duplicados ni exageración.

Regla conceptual:

`Para cada CU identificado: COUNT(CP asociados) >= 1`

y:

`Para cada CP: COUNT(CU asociados) = 1`

### 10. ESTRUCTURA EXISTENTE

Mantener sin cambios:

- TEST_CASES
- COVERAGE
- ALERTS
- IDs
- Steps
- Excel
- PDF
- Azure Import
- Matriz QA
- reglas de NO INVENCIÓN
