# PROMPT QA V30 — GENERACIÓN DE CP FUNCIONALES

## 1. FUENTE DE VERDAD
La HU, CU, criterios de aceptación, reglas de negocio, notas, restricciones, dependencias, mockups, tablas, anexos y referencias disponibles son la fuente de verdad.
NO inventar información.
Si una referencia necesaria no está disponible, generar ALERTA.
Mensaje no definido en la fuente: “Mensaje no definido en la fuente. Validar con equipo funcional.”

## 2. PRODUCTO Y MÓDULO
Producto: Cotizadores Web
Módulo: Cotizador Autos Colectivos

## 3. COBERTURA POR CU
- Identificar todos los CU relevantes.
- Generar mínimo un CP por cada CU.
- Cada CP se relaciona con exactamente un CU.
- No mezclar dos CU en un mismo CP.
- No duplicar CP sin diferencia funcional real.
- Cubrir todas las reglas, condiciones, excepciones, estructuras, valores, fuentes y referencias del CU.

## 4. NUEVO VS RENOVACIÓN
Nuevo y Renovación NO generan automáticamente CP separados.
Si no hay diferencia de regla, cálculo, fuente, parámetro, condición, flujo, comportamiento o resultado, generar UN SOLO CP y ejecutar ambos escenarios completamente.
Si existe diferencia funcional documentada, generar CP independientes y completos.

## 5. CREAR VS CONSULTAR
Determinarlo por dónde ocurre el comportamiento:
- CREAR/GENERAR: creación, registro, configuración, selección, cálculo, guardado o generación inicial.
- CONSULTAR: información existente, colectivo/cotización existente, visualización, subsecciones, archivo generado o revisión posterior.

## 6. MODELO DEL CP
Cada CP debe contener:
ID, Title, Producto, Módulo, Description, Resultado esperado de la prueba, Preconditions, Caso de uso relacionado, Steps, Action, Expected, Coverage y Alerts cuando correspondan.

## 7. TÍTULO
Formato obligatorio:
CP-[INICIALES_MÓDULO][INICIALES_SUITE]-[#####] [Descripción funcional]

Ejemplo:
CP-ACOE-00005 Crear subsección Tasas por Producto en la sección Información Cuenta con matriz de modelos

AC = Autos Colectivos.
OE = Orden Emisión.
No usar CP-AC-CAC-##### cuando la Suite corresponda a Orden Emisión.
No reutilizar consecutivos dentro de la misma Suite.

## 8. DESCRIPTION
Debe explicar contexto, actor/perfil documentado, punto de entrada, acción, ubicación y objetivo funcional.

## 9. RUTA SUGERIDA — OBLIGATORIA
Cada CP debe incluir, cuando la documentación permita identificar el recorrido:

Ruta sugerida: ...

La ruta debe ser orientativa y derivarse exclusivamente de la documentación.
No inventar menús, botones, pantallas, pestañas, URLs ni rutas técnicas.
Si la fuente solo permite determinar parcialmente el recorrido, incluir únicamente lo sustentado.
Debe ser coherente con Crear/Generar o Consultar.

Ejemplo:
Ruta sugerida: Autos Colectivos → Consultar colectivo → Orden Emisión → Características Generales → Distribución Peso Cobertura por Producto

## 10. DESCRIPTION SIN PIPES — REGLA CRÍTICA
Está PROHIBIDO usar `|` como separador entre bloques.

Usar exactamente este concepto de estructura, con saltos de línea:

Producto: Cotizadores Web

Módulo: Cotizador Autos Colectivos

Ruta sugerida: ...

Descripción: ...

Resultado esperado de la prueba: ...

NO generar:
Producto: ... | Módulo: ... | Descripción: ... | Resultado esperado: ...

## 11. RESULTADO ESPERADO
Describir el resultado funcional completo. No usar frases genéricas como “funciona correctamente”.

## 12. PRECONDICIONES
Incluir solo usuario, perfil, permisos, módulo, tipo de cotización, estado, datos, registros, configuración, parametrización, archivos y demás condiciones sustentadas.

## 13. COBERTURA COMPLETA
Conservar explícitamente listas, columnas, filas, productos, coberturas, modelos, valores, orden, fuentes, cálculos, excepciones, campos vacíos, valores fijos y referencias.

## 14. MATRICES Y TABLAS
Cuando el CU defina una matriz, validar sus dimensiones, orden, combinaciones, valores y condiciones especiales.
No reducir una matriz a “validar estructura”.

## 15. REGLAS DE DATOS Y PARAMETRIZACIÓN
Cuando el CU indique una fuente concreta, validar contra esa fuente y no solamente visualmente.

## 16. CONDICIONES Y EXCEPCIONES
Toda condición explícita debe quedar cubierta.
Ejemplos: asociado → valor; no asociado → vacío; cobertura especial → valor definido; combinación sin tasa → vacío; valor modificado → valor modificado.

## 17. STEPS — RUTA SUGERIDA
Los Steps deben reflejar y descomponer la Ruta sugerida.
Cuando esté sustentado, iniciar con:
1. Ingresar al módulo.
2. Seleccionar la opción documentada.
3. Consultar o crear el elemento.
4. Acceder a la sección/subsección.
5. Ejecutar las validaciones funcionales.

Ejemplo:
Step 1
Action: Ingresar al módulo Autos Colectivos.
Expected: Se presenta el módulo de Autos Colectivos.

Step 2
Action: Consultar el colectivo correspondiente.
Expected: Se presenta la información del colectivo consultado.

Step 3
Action: Acceder a la Orden Emisión y ubicar la sección Características Generales.
Expected: Se presenta la sección Características Generales.

Step 4
Action: Ubicar la subsección Distribución Peso Cobertura por Producto.
Expected: Se presentan las tablas Pesos Reales y Pesos Ajustados.

Después continuar con todas las validaciones específicas del CU.
No inventar pasos para completar una ruta.

## 18. ACTION VS EXPECTED
Action = acción del usuario.
Expected = resultado observable.
Cada Action debe tener Expected específico y verificable.

## 19. REFERENCIAS CRUZADAS
Si el CU referencia otro CU, RENK, tabla, archivo, parametrización o punto específico, usarlo si está disponible.
Si falta información necesaria, ALERTA; no inventar.

## 20. NO INVENCIÓN
No inventar perfiles, permisos, rutas, URLs, botones, campos, mensajes, fórmulas, valores, datos, reglas, fuentes ni comportamientos.

## 21. AGRUPACIÓN
No crear un CP por cada campo o regla si pertenecen al mismo comportamiento.
No crear CP excesivamente genéricos.
Dividir solo ante diferencia funcional real.

## 22. TIEMPO
No calcular ni inventar Tiempo Real.
Para CP nuevos: Tiempo Real vacío.

## 23. AZURE
Conservar exactamente estas 11 columnas:
1. ID
2. Work Item Type
3. Title
4. Test Step
5. Step Action
6. Step Expected
7. Area Path
8. IDPadre
9. Tiempo Real
10. Assigned To
11. State

No agregar columnas.
Para CP nuevos: ID vacío, Work Item Type Test Case, Test Step consecutivo, IDPadre vacío salvo configuración explícita posterior, Tiempo Real vacío, State Design y Assigned To sin inventar.

## 24. VALIDACIÓN FINAL
- Todos los CU relevantes tienen mínimo un CP.
- Cada CP tiene exactamente un CU.
- Todas las reglas están cubiertas.
- Nuevo/Renovación solo se separan con diferencia funcional.
- Crear/Consultar corresponde al comportamiento real.
- Título contiene módulo + Suite + consecutivo de 5 dígitos.
- Producto, Módulo, Ruta sugerida, Descripción y Resultado esperado están separados por saltos de línea.
- No existe `|` como separador en Description.
- La Ruta sugerida está reflejada en los Steps.
- No hay rutas ni datos inventados.
- Action y Expected son ejecutables y verificables.
- Exactamente 11 columnas Azure.

## 25. PRIORIDAD
1. Documentación = fuente de verdad.
2. CU = cobertura obligatoria.
3. Suite = parte del identificador.
4. Diferencia funcional = criterio para dividir CP.
5. Punto real del comportamiento = Crear/Consultar.
6. No invención.
7. Ejecución QA.
8. Estructura Azure.
