# PROMPT QA — COBERTURA, PRODUCTO/MÓDULO Y EXCEL AZURE

## 1. COBERTURA OBLIGATORIA

Cada Caso de Uso (CU) identificado en la documentación DEBE tener como mínimo un Caso de Prueba (CP) propio.

Regla estricta:

**1 CP = 1 CU.**

No relacionar un mismo CP con varios CU.
No agrupar funcionalidades diferentes aunque pertenezcan a la misma HU, módulo, pantalla o flujo.

Cada CU debe aparecer individualmente en COVERAGE y tener al menos un CP.

## 2. ESCENARIOS ADICIONALES

Después de garantizar el mínimo de un CP por CU, crear CP adicionales únicamente cuando la documentación sustente un comportamiento funcional diferente.

No exagerar.
No duplicar.
No fragmentar artificialmente.
No inventar escenarios mediante técnicas QA genéricas no sustentadas.

## 3. PRODUCTO Y MÓDULO

Cuando la documentación corresponda a Autos Colectivos del aplicativo:

- Producto: `Cotizadores Web`
- Módulo: `Cotizador Autos Colectivos`

Usar exactamente estas denominaciones.

No usar variantes.

Si la documentación corresponde a otro producto o módulo, no imponer estos valores.

## 4. NO INVENCIÓN

No inventar campos, datos, mensajes, reglas, perfiles, permisos, navegación ni resultados.

Si falta información, generar DRAFT y ALERTA.

## 5. EXCEL PARA AZURE DEVOPS TEST PLANS

La aplicación debe generar una hoja llamada:

`Azure Import`

Esta hoja debe ser directamente compatible con la importación masiva de Test Cases de Azure DevOps.

Debe contener EXACTAMENTE estos 9 encabezados:

1. `ID`
2. `Work Item Type`
3. `Title`
4. `Test Step`
5. `Step Action`
6. `Step Expected`
7. `Area Path`
8. `Assigned To`
9. `State`

### Reglas de valores

- `ID`: dejar vacío para CP nuevos. No colocar aquí el ID funcional `CP-AC-...`.
- `Work Item Type`: exactamente `Test Case`.
- `Title`: incluir el ID funcional del agente, por ejemplo `CP-AC-AUTO-00001 - ...`.
- `Test Step`: numeración secuencial 1, 2, 3...
- `Step Action`: acción que realiza el tester.
- `Step Expected`: resultado esperado de ese paso.
- `Area Path`: debe corresponder a una ruta real existente en el proyecto Azure. No inventar.
- `Assigned To`: debe ser un usuario real de la organización. No inventar.
- `State`: exactamente `Design` para nuevos CP.

### Regla de filas

Cada Step debe ser una fila independiente.

Para todas las filas pertenecientes al mismo CP se deben repetir:

- ID
- Work Item Type
- Title
- Area Path
- Assigned To
- State

El `Test Step` cambia secuencialmente y también cambian `Step Action` y `Step Expected`.

### Ejemplo

ID | Work Item Type | Title | Test Step | Step Action | Step Expected | Area Path | Assigned To | State
| | Test Case | CP-AC-AUTO-00001 - Crear cotización | 1 | Ingresar al cotizador | Se muestra el cotizador | [ruta real] | [usuario real] | Design
| | Test Case | CP-AC-AUTO-00001 - Crear cotización | 2 | Seleccionar Autos Colectivos | Se muestra el módulo | [ruta real] | [usuario real] | Design

## 6. MATRIZ QA

La hoja `Matriz QA` debe conservar exactamente las columnas ya aprobadas por el proyecto.

No agregar columnas adicionales a la Matriz QA por este ajuste.

## 7. VALIDACIÓN FINAL

Antes de entregar:

- Todos los CU tienen mínimo un CP.
- Cada CP tiene exactamente un CU.
- No existen CP relacionados con varios CU.
- Producto y Módulo usan la nomenclatura definida cuando corresponda.
- La hoja Azure Import tiene exactamente los 9 encabezados oficiales.
- Los CP nuevos tienen ID vacío en la columna Azure `ID`.
- Cada Step es una fila.
- Los campos requeridos de Azure se mantienen consistentes.
- State = `Design`.
