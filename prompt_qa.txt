============================================================
AJUSTES VIGENTES — GENERACIÓN QA MAIN
============================================================

REGLA 1 — COBERTURA OBLIGATORIA DE TODOS LOS CU

Antes de generar cualquier CP debes identificar TODOS los CU presentes en la
documentación.

Construye internamente una matriz:

CU → CP

La generación SOLO es válida cuando:

- cada CU identificado tiene mínimo un CP;
- cada CP tiene exactamente un CU relacionado;
- ningún CU queda sin CP;
- ningún CP queda sin CU válido;
- ningún CP queda relacionado con más de un CU.

No priorices generar muchos CP sobre cubrir todos los CU.

Si existen 21 CU, la respuesta debe cubrir los 21 CU como mínimo.

Nunca entregues una generación parcial como válida.

EJEMPLO INVÁLIDO:

6/21 CU cubiertos.

15/21 CU cubiertos.

20/21 CU cubiertos.

En cualquiera de estos casos debes continuar/corregir la generación antes de
entregarla.

============================================================
REGLA 2 — MATRIZ INTERNA ANTES DE GENERAR
============================================================

Antes de construir TEST_CASES realiza internamente:

1. Identificar CU.
2. Identificar nombre de cada CU.
3. Crear una fila por CU.
4. Asignar mínimo un CP a cada CU.
5. Identificar si necesita más de un CP por diferencia funcional.
6. Generar los CP.
7. Auditar nuevamente CU → CP.

No debes generar primero algunos CP y después intentar completar los CU
restantes de forma improvisada.

============================================================
REGLA 3 — UN SOLO CU POR CP
============================================================

Cada CP debe tener exactamente:

"Related Use Case": "CU-XXX - Nombre exacto del CU"

No colocar dos o más CU en Related Use Case.

No utilizar referencias como:

"CU-328 / CU-329"

"CU-328, CU-329"

"CU-328 y CU-329"

Si el CP necesita cubrir dos CU diferentes, debes dividirlo en dos CP.

============================================================
REGLA 4 — TÍTULO
============================================================

El título debe seguir exactamente:

CP-[INICIALES_MODULO][INICIALES_SUITE]-##### [DESCRIPCIÓN]

Para Autos Colectivos:

AC = módulo.

Las siguientes iniciales corresponden a la Suite funcional.

Ejemplo:

CP-ACOE-00005 Crear subsección Tasas por Producto en la sección Información
Cuenta con matriz de modelos

El título debe ser descriptivo.

Debe indicar qué funcionalidad se está validando.

No utilizar títulos genéricos:

"Validar CU-332"

"Prueba CU-332"

"Validar funcionalidad"

"Validación de CU"

No colocar pipes "|" en el título.

============================================================
REGLA 5 — DESCRIPCIÓN DE NIVEL QA
============================================================

La Description debe ser suficientemente detallada para que un QA pueda
ejecutar el CP sin tener que interpretar nuevamente el CU.

La Description debe incluir, cuando estén documentados:

- perfil;
- punto de entrada;
- ruta;
- módulo;
- icono;
- menú;
- opción;
- estado;
- archivo;
- hoja;
- sección;
- subsección;
- tabla;
- filas;
- columnas;
- productos;
- coberturas;
- orden;
- parametrizaciones;
- reglas;
- cálculos;
- fuentes;
- condiciones;
- excepciones;
- homologaciones;
- valores fijos;
- valores vacíos.

No reduzcas una regla compleja a una frase genérica.

Ejemplo incorrecto:

"Validar homologación de productos nuevos."

Ejemplo correcto:

"Validar que para los productos nuevos se realice la homologación tomando
la agrupación con mayor cantidad de vehículos según Tipo de Vehículo + Uso +
Alta Gama, identificando el producto base que tenga la misma agrupación y
todas las coberturas básicas, para asignar al producto nuevo la distribución
correspondiente."

============================================================
REGLA 6 — RUTA FUNCIONAL
============================================================

La ruta funcional NO debe aparecer como un campo independiente.

NO crear:

Ruta sugerida:
Ruta estimada:
Ruta funcional:
Navegación:

La ruta debe formar parte de la Description.

Usa los Test Cases reales de Azure DevOps seleccionados como referencia para
identificar el patrón de navegación, perfil y terminología.

Ejemplo del estándar aprobado:

"Ingresar con usuario del perfil suscriptor, seleccionar el icono de autos
colectivos, consultar colectivo en estado cotizado, descargar el archivo base
emisión y validar que la hoja Orden Emisión, en la sección Características
Generales, contenga la subsección..."

La ruta debe llegar hasta el punto donde ocurre la funcionalidad del CU.

NO inventar una ruta que no esté soportada por la documentación o por el CP
de referencia.

============================================================
REGLA 7 — CP DE REFERENCIA
============================================================

Cuando la usuaria seleccione un Test Case de Azure como referencia:

UTILIZARLO para:

- perfil;
- navegación;
- punto de entrada;
- nombres de opciones;
- nombres de pantallas;
- nombres de hojas;
- nombres de secciones;
- estilo;
- nivel de detalle;
- estructura de pasos.

NO utilizarlo para inventar reglas del CU actual.

La funcionalidad y reglas siempre provienen del CU que se está procesando.

============================================================
REGLA 8 — REFINAMIENTO DEL CU
============================================================

El refinamiento del CU forma parte de la fuente funcional.

Si el CU contiene una regla específica, esa regla debe aparecer en el CP
cuando sea necesaria para ejecutar la prueba.

Esto incluye:

- cálculos;
- fórmulas;
- fuentes;
- parametrizaciones;
- condiciones;
- agrupaciones;
- homologaciones;
- orden;
- coberturas;
- valores;
- excepciones.

No resumir el refinamiento hasta perder la regla que debe validarse.

============================================================
REGLA 9 — NUEVO Y RENOVACIÓN
============================================================

NO dividir automáticamente un CU en Nuevo y Renovación.

Si ambos tienen exactamente la misma regla funcional:

- un solo CP;
- mencionar ambos escenarios;
- ejecutar la validación para ambos.

Si existe diferencia funcional en:

- regla;
- cálculo;
- fuente;
- parámetro;
- condición;
- comportamiento;
- flujo;
- resultado;

crear CP independientes.

============================================================
REGLA 10 — CREAR VS CONSULTAR
============================================================

Determina el verbo principal del CP según dónde ocurre la funcionalidad.

CREAR:

cuando la validación ocurre durante creación, configuración, selección,
registro o guardado.

CONSULTAR:

cuando la validación ocurre sobre un colectivo/cotización existente,
visualización, subsección o archivo generado.

No utilizar "Crear" únicamente porque el nombre del CU empieza por "Crear".

============================================================
REGLA 11 — STEPS
============================================================

Cada Step debe contener:

Step #
Action
Expected value

Action = acción realizada por QA.

Expected value = resultado observable del sistema.

Los pasos deben seguir la ruta funcional.

Los pasos deben cubrir las reglas principales del CU.

No colocar toda la prueba en un único Step.

============================================================
REGLA 12 — FORMATO DE DESCRIPTION
============================================================

Mantener exactamente:

Producto:

Módulo:

Descripción:

Resultado esperado de la prueba:

Precondiciones:

Caso de uso relacionado:

Cada bloque debe estar separado visualmente.

Utilizar saltos de línea reales.

NO utilizar:

\n

/n

\r

como texto visible.

NO compactar todos los campos en una sola línea.

============================================================
REGLA 13 — PROHIBIDO PIPE
============================================================

El carácter:

|

está PROHIBIDO en cualquier campo generado.

No utilizarlo en:

- Title;
- Description;
- Expected Result;
- Preconditions;
- Related Use Case;
- Action;
- Expected value;
- Coverage;
- Alerts.

Si una fuente contiene un pipe, conserva el significado sin generar el
carácter.

============================================================
REGLA 14 — CASO DE USO RELACIONADO
============================================================

Cada CP debe terminar/conservar:

Caso de uso relacionado:

CU-XXX - Nombre exacto del CU

Debe corresponder al CU real que origina el CP.

Nunca dejarlo vacío.

Nunca colocar un CU diferente.

============================================================
REGLA 15 — VALIDACIÓN ANTES DE ENTREGAR
============================================================

Antes de devolver TEST_CASES debes comprobar internamente:

A. Cobertura:

CU identificados = CU cubiertos.

B. Trazabilidad:

Cada CP tiene exactamente un CU.

C. Títulos:

Todos siguen:

CP-[MODULO][SUITE]-##### ...

D. Description:

Tiene ruta funcional cuando está sustentada.

E. Detalle:

Incluye el refinamiento necesario.

F. Formato:

No pipes.

No /n.

No \n literal.

No escapes visibles.

G. Steps:

Action y Expected separados.

H. Escenarios:

Nuevo/Renovación solo se separan cuando existe diferencia funcional.

============================================================
REGLA 16 — PRIORIDAD
============================================================

La prioridad de generación es:

1. Documentación/HU/CU.
2. Cobertura completa de todos los CU.
3. Refinamiento funcional.
4. CP de referencia de Azure para navegación.
5. Título.
6. Description.
7. Steps.
8. Formato Azure.
9. No invención.

NO sacrificar la cobertura completa de CU para generar CP más elaborados.

Primero garantiza que TODOS los CU tengan CP.

Después mejora el nivel de detalle de cada CP.
