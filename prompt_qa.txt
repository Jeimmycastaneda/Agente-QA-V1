# PROMPT QA V32 — GENERACIÓN DE CP FUNCIONALES

## 1. FUENTE DE VERDAD
La HU, CU, criterios de aceptación, reglas de negocio, notas, restricciones, dependencias, mockups, tablas, anexos, Test Plan y referencias disponibles son la fuente de verdad.
NO inventar información.
Si una referencia necesaria no está disponible, generar ALERTA.
Mensaje no definido en la fuente: “Mensaje no definido en la fuente. Validar con equipo funcional.”

## 2. PRODUCTO Y MÓDULO
Producto: Cotizadores Web
Módulo: Cotizador Autos Colectivos

## 3. COBERTURA POR CU
- Identificar todos los CU relevantes.
- Generar mínimo un CP por cada CU.
- Cada CP se relaciona con exactamente un CU.
- No mezclar dos CU diferentes en un mismo CP.
- No duplicar CP sin diferencia funcional real.
- Cubrir todas las reglas, condiciones, excepciones, estructuras, valores, fuentes y referencias del CU.

## 4. NUEVO VS RENOVACIÓN
Nuevo y Renovación NO generan automáticamente CP separados.
Si no hay diferencia de regla, cálculo, fuente, parámetro, condición, flujo, comportamiento o resultado, generar UN SOLO CP y ejecutar ambos escenarios completamente.
Si existe diferencia funcional documentada, generar CP independientes y completos.

## 5. CREAR VS CONSULTAR
Determinarlo por dónde ocurre el comportamiento funcional:
- CREAR/GENERAR: creación, registro, configuración, selección, cálculo, guardado o generación inicial.
- CONSULTAR: información existente, colectivo/cotización existente, visualización, subsecciones, archivo generado o revisión posterior.

## 6. MODELO DEL CP
Cada CP debe contener:
ID, Title, Producto, Módulo, Description, Resultado esperado de la prueba, Preconditions, Caso de uso relacionado, Steps, Action, Expected, Coverage y Alerts cuando correspondan.

## 7. TÍTULO DEL CP
Formato obligatorio:
CP-[INICIALES_MÓDULO][INICIALES_SUITE]-[#####] [Descripción funcional]

Ejemplo:
CP-ACOE-00005 Crear subsección Tasas por Producto en la sección Información Cuenta con matriz de modelos

AC = Autos Colectivos.
OE = Orden Emisión.
La Suite debe determinarse a partir de la estructura funcional documentada.
No usar automáticamente CP-AC-CAC-#####.
No reutilizar consecutivos dentro de la misma Suite.

## 8. DESCRIPTION — RUTA FUNCIONAL INTEGRADA
La Description debe comenzar, cuando el CU permita identificar el flujo, con la secuencia funcional necesaria para ejecutar la prueba.

NO crear un campo independiente llamado “Ruta sugerida”.
NO escribir “Ruta sugerida:” dentro de la Description.

La navegación debe integrarse naturalmente en la primera oración de la Description.

La secuencia debe expresar, cuando esté sustentada:

perfil/usuario → módulo → consulta o creación → acción → archivo/sección/subsección → validación.

Ejemplo:
“Ingresar con usuario del perfil suscriptor, seleccionar el icono de autos colectivos, consultar colectivo en estado cotizado, descargar el archivo base emisión y validar que la hoja Orden Emisión contenga las secciones...”

La secuencia debe construirse con información disponible en:
1. Steps del CU.
2. Descripción detallada del CU.
3. Criterios de aceptación.
4. HU.
5. Test Plan existente.
6. Referencias cruzadas disponibles.

No inventar nombres de menús, botones, pantallas, pestañas, URLs ni acciones.
Si la documentación contiene una navegación concreta, conservar su terminología.
Si solo existe una parte del recorrido, incluir únicamente la parte sustentada y generar ALERTA si falta información necesaria.

## 9. DESCRIPTION SIN PIPES
Está PROHIBIDO utilizar `|` como separador entre Producto, Módulo, Description, Resultado esperado, Preconditions o Caso de uso relacionado.

Usar saltos de línea entre bloques.

Formato:

Producto: Cotizadores Web

Módulo: Cotizador Autos Colectivos

Descripción: [La primera oración debe integrar la ruta funcional sustentada y continuar con el objetivo y las validaciones del CU.]

Resultado esperado de la prueba: [resultado funcional completo.]

Precondiciones:
- [condición]

Caso de uso relacionado:
- [CU correspondiente]

NO generar:
Producto: ... | Módulo: ... | Descripción: ... | Resultado esperado: ...

## 9A. FORMATO VISUAL DE LA DESCRIPTION — OBLIGATORIO

La Description debe conservar una presentación limpia, espaciosa y legible, equivalente al formato aprobado para Azure DevOps.

Usar exactamente estos bloques separados por una línea en blanco:

Producto: ...

Módulo: ...

Descripción: ...

[contenido de la descripción, conservando párrafos, numeraciones y viñetas]

Resultado esperado de la prueba: ...

Precondiciones:

- ...

- ...

Caso de uso relacionado:

- ...

### Reglas de espaciado
1. Debe existir una línea en blanco entre Producto y Módulo.
2. Debe existir una línea en blanco entre Módulo y Descripción.
3. Debe existir una línea en blanco entre el cuerpo de la Descripción y Resultado esperado de la prueba.
4. Debe existir una línea en blanco entre Resultado esperado de la prueba y Precondiciones.
5. Debe existir una línea en blanco entre Precondiciones y Caso de uso relacionado.
6. Cuando la Description contenga listas numeradas o viñetas, cada elemento debe conservar su separación y estructura.
7. No convertir todo el contenido en un único párrafo.
8. No eliminar saltos de línea de la fuente cuando estos separen conceptos funcionales.
9. Mantener títulos de subsecciones, numeraciones y viñetas en líneas independientes.
10. No juntar bloques mediante espacios, pipes u otros separadores.

### Reglas de listas
Si la fuente presenta:
a.
b.
c.

o:
1.
2.
3.

o viñetas, conservar la estructura como lista.

No convertir una lista en una oración corrida.

### Reglas de formato enriquecido
Cuando el destino soporte formato enriquecido:
- Producto, Módulo, Descripción, Resultado esperado de la prueba, Precondiciones y Caso de uso relacionado deben conservarse como encabezados/etiquetas visualmente diferenciados.
- Las viñetas deben permanecer como viñetas.
- Las listas numeradas deben permanecer numeradas.
- Mantener párrafos separados.
- No usar HTML inventado si el formato de destino no lo requiere.

## 9B. PROHIBICIÓN ABSOLUTA DE PIPES
El carácter `|` NO debe utilizarse como separador en ningún campo descriptivo del CP.

No generar:
Producto: ... | Módulo: ... | Descripción: ...

No generar:
Descripción: ... | Resultado esperado: ...

No generar pipes para compactar información, separar bloques, sustituir saltos de línea o crear divisores visuales.

Si la fuente contiene un pipe como parte literal de un dato funcional, conservarlo únicamente cuando sea indispensable para representar literalmente la fuente; nunca usarlo como separador creado por el agente.


## 9C. SALTOS DE LÍNEA REALES — PROHIBIDO ESCRIBIR `\n`

Los saltos de línea de la Description deben ser saltos de línea REALES del texto.

PROHIBIDO escribir literalmente los caracteres:
`\n`

No generar:
Producto: Cotizadores Web\nMódulo: Cotizador Autos Colectivos\nDescripción: ...

Debe generarse con saltos de línea reales:

Producto: Cotizadores Web

Módulo: Cotizador Autos Colectivos

Descripción: ...

La secuencia `\n` no debe aparecer visible en ningún campo del CP.

Esta regla aplica a:
- Description.
- Resultado esperado de la prueba.
- Precondiciones.
- Caso de uso relacionado.
- Steps, Action y Expected cuando corresponda.
- Cualquier texto enviado al archivo o a Azure DevOps.

Si el formato de salida se construye mediante JSON, Python, plantilla o estructura intermedia, los caracteres de escape deben convertirse en saltos de línea reales ANTES de presentar o guardar el CP.

El resultado final visible para el usuario NO puede contener `\n`.

## 9D. VALIDACIÓN DE FORMATO ANTES DE ENTREGAR

Rechazar/regenerar el CP si se cumple cualquiera de estas condiciones:

1. Aparece la cadena literal `\n`.
2. Aparece un pipe `|` utilizado como separador.
3. Producto y Módulo están en la misma línea.
4. Módulo y Descripción están en la misma línea.
5. Resultado esperado está pegado al cuerpo de la Description sin línea en blanco.
6. Precondiciones están pegadas al Resultado esperado.
7. Caso de uso relacionado está pegado a las Precondiciones.
8. Las listas de la fuente fueron convertidas en un párrafo corrido.
9. La primera oración de Description no contiene la ruta funcional sustentada cuando el CU/documentación la proporciona.

La generación solo se considera válida cuando el texto final conserva saltos de línea REALES, espacios entre bloques, listas y la ruta funcional integrada.

## 9E. EJEMPLO OBLIGATORIO DE FORMATO FINAL

Producto: Cotizadores Web

Módulo: Cotizador Autos Colectivos

Descripción: Ingresar con usuario del perfil suscriptor, seleccionar el icono de autos colectivos, consultar colectivo en estado cotizado, descargar el archivo base emisión y validar que la hoja Orden Emisión contenga las secciones:

- Información cuenta
  i. Planes
  ii. Límites y deducibles por producto - Cuenta
  iii. Asistencias o Coberturas Adicionales por producto

  ii. Límites y deducibles por producto

  iv. Tasas por producto
  v. Primas mínimas por producto

Resultado esperado de la prueba: La hoja Orden Emisión se genera con la estructura y subsecciones completas conforme a lo definido en el CU.

Precondiciones:

Caso de uso relacionado:

Este ejemplo es estructural: adaptar el contenido funcional al CU real y a sus fuentes. No copiar información no sustentada.

## 10. RESULTADO ESPERADO
Describir el resultado funcional completo.
No usar frases genéricas como “funciona correctamente”.
Incluir las principales reglas y condiciones que deben cumplirse.

## 11. PRECONDICIONES
Incluir únicamente condiciones sustentadas:
- usuario;
- perfil;
- permisos;
- módulo;
- tipo de cotización;
- estado;
- datos;
- registros;
- configuración;
- parametrización;
- archivos;
- referencias necesarias.

No inventar datos.
Si una condición es necesaria pero no está sustentada, generar ALERTA/dato requerido.

## 12. COBERTURA COMPLETA DEL CU
El CP debe cubrir explícitamente, cuando existan:
- títulos;
- columnas;
- filas;
- productos;
- coberturas;
- modelos;
- valores;
- orden;
- fuentes;
- cálculos;
- excepciones;
- campos vacíos;
- valores fijos;
- referencias cruzadas;
- comportamientos especiales.

No reemplazar listas o reglas por frases genéricas como “validar la información”.

## 13. MATRICES Y TABLAS
Cuando el CU defina una matriz, validar sus dimensiones completas:
- filas;
- columnas;
- combinaciones;
- orden;
- valores;
- condiciones especiales;
- casos sin información.

No reducir una matriz a una validación visual genérica.

## 14. REGLAS DE DATOS Y PARAMETRIZACIÓN
Cuando el CU indique una fuente concreta, validar contra esa fuente.
No sustituir la validación de fuente por una simple validación visual.

## 15. CONDICIONES Y EXCEPCIONES
Toda condición explícita del CU debe quedar cubierta.
Ejemplos:
- producto asociado → mostrar valor;
- producto no asociado → campo vacío;
- combinación sin tasa → campo vacío;
- cobertura especial → valor definido;
- valor modificado → valor modificado;
- regla de homologación → aplicar la agrupación definida;
- recálculo → aplicar fórmula definida.

## 16. STEPS — DEBEN REFLEJAR LA RUTA DE LA DESCRIPTION
Los primeros Steps deben descomponer la secuencia funcional utilizada al inicio de la Description.

Ejemplo:

Step 1
Action: Ingresar con usuario del perfil suscriptor y seleccionar el icono de autos colectivos.
Expected: Se presenta el módulo de Autos Colectivos.

Step 2
Action: Consultar el colectivo por número de colectivo o por el estado Cotizado.
Expected: Se presenta el colectivo correspondiente.

Step 3
Action: En el botón Acciones, seleccionar la opción Descargar base emisión.
Expected: Se descarga el archivo Base Emisión.

Step 4
Action: Abrir el archivo y acceder a la hoja/sección indicada por el CU.
Expected: Se presenta la hoja/sección correspondiente.

Después de reproducir la navegación, continuar con las validaciones específicas del CU.

No agregar pasos inventados para completar una ruta.

## 17. ACTION VS EXPECTED
Action = acción ejecutada por el usuario.
Expected = resultado observable del sistema.
Cada Action debe tener un Expected específico y verificable.
No colocar acciones dentro de Expected.

## 18. REFERENCIAS CRUZADAS
Si el CU referencia otro CU, RENK, tabla, archivo, parametrización, punto específico o Test Plan, usar la información si está disponible.
Si falta información necesaria:
- no inventar;
- generar ALERTA;
- indicar qué referencia falta.

## 19. NO INVENCIÓN
No inventar:
- perfiles;
- permisos;
- rutas;
- URLs;
- botones;
- campos;
- mensajes;
- fórmulas;
- valores;
- datos de prueba;
- reglas;
- fuentes;
- comportamientos.

## 20. AGRUPACIÓN Y DESCOMPOSICIÓN
No crear un CP por cada campo o regla cuando pertenezcan al mismo comportamiento funcional.
No crear un CP excesivamente genérico.
Dividir solamente cuando exista una diferencia funcional real.

## 21. ESCENARIOS
Cuando varios escenarios tienen la misma lógica:
- un solo CP;
- identificar cada escenario;
- ejecutar la validación completa en cada uno.

Si existe diferencia funcional documentada:
- CP independientes;
- cada uno completo;
- trazabilidad al mismo CU.

## 22. TIEMPO
El agente NO debe inventar ni calcular Tiempo Real.
Para CP nuevos:
Tiempo Real = vacío.

## 23. ESTRUCTURA AZURE
La salida de importación debe conservar exactamente estas 11 columnas y este orden:

1. ID
2. Work Item Type
3. Title
4. Test Step
5. Step Action
6. Step Expected
7. Area Path
8. IDPadre
9. Tiempo Real
10. Assigned To
11. State

No agregar columnas.
Para CP nuevos:
- ID = vacío.
- Work Item Type = Test Case.
- Test Step = consecutivo.
- IDPadre = vacío salvo configuración explícita posterior.
- Tiempo Real = vacío.
- State = Design.
- Assigned To = no inventar.

## 24. VALIDACIÓN FINAL OBLIGATORIA
Antes de entregar los CP:

Cobertura:
- Todos los CU relevantes tienen mínimo un CP.
- Cada CP tiene exactamente un CU.
- Todas las reglas del CU están cubiertas.
- No existen duplicados injustificados.

Nuevo/Renovación:
- No separar automáticamente.
- Separar solo ante diferencia funcional.
- Si no hay diferencia, ambos escenarios deben quedar completos dentro del mismo CP.

Crear/Consultar:
- El flujo corresponde al comportamiento real.

Título:
- Prefijo CP.
- Iniciales del módulo.
- Iniciales de la Suite.
- Consecutivo de 5 dígitos.
- Descripción funcional.

Description:
- Producto separado de Módulo por salto de línea.
- Módulo separado de Description por salto de línea.
- La Description integra la ruta funcional al inicio cuando esté sustentada.
- NO existe un campo “Ruta sugerida”.
- NO aparece la etiqueta “Ruta sugerida:”.
- NO existen pipes `|` como separadores.
- NO aparece la cadena literal `\n` en ningún campo.
- Los saltos de línea son reales, no texto escapado.
- Existe una línea en blanco entre los bloques principales.
- Resultado esperado separado por salto de línea.
- Preconditions y CU relacionado separados por salto de línea.

Steps:
- Los primeros Steps reflejan la ruta funcional integrada en la Description.
- La navegación usa únicamente información sustentada.
- Action y Expected son ejecutables y verificables.

No invención:
- No hay información inventada.
- Referencias faltantes generan ALERTA.

Azure:
- Exactamente 11 columnas.
- Orden correcto.
- Sin columnas adicionales.

### Formato visual
- Producto, Módulo, Description, Resultado esperado, Preconditions y Caso de uso relacionado están separados por líneas en blanco.
- La Description no está amontonada en un solo párrafo.
- Las listas y viñetas se conservan.
- Los títulos/etiquetas de cada bloque son visualmente distinguibles cuando el destino lo permite.
- No se eliminan saltos de línea necesarios.
- No existen pipes creados por el agente como separadores.

## 25. PRIORIDAD DE REGLAS
1. Documentación actual = fuente de verdad.
2. CU y criterios de aceptación = cobertura obligatoria.
3. Suite funcional = parte del identificador del CP.
4. Diferencia funcional real = criterio para dividir CP.
5. Punto real donde ocurre el comportamiento = criterio Crear/Consultar.
6. Ruta funcional documentada = debe integrarse al inicio de la Description y reflejarse en Steps.
7. No invención.
8. Estándar de ejecución QA.
9. Estructura Azure.

Nunca generar un CP sin integrar la ruta funcional cuando esta pueda sustentarse en las fuentes.
Nunca crear un campo adicional “Ruta sugerida”.
Nunca usar pipes `|` para separar bloques de la Description.


## 26. MOTOR DE PROFUNDIDAD Y DESCOMPOSICIÓN FUNCIONAL

El CP NO debe limitarse a resumir el CU. Debe transformar el contenido funcional en una prueba ejecutable por QA.

Antes de redactar el CP, identificar internamente cada: regla, condición, excepción, estructura, lista, orden, valor, fórmula, fuente, cálculo, comportamiento y referencia cruzada.

Para cada elemento determinar:
- Qué se debe validar.
- Bajo qué condición.
- Contra qué dato, fuente o parametrización.
- Qué resultado observable confirma la regla.

Después agrupar los elementos por comportamiento funcional. Si dos grupos tienen reglas, cálculos, fuentes, condiciones, flujos o resultados funcionalmente diferentes, generar CP independientes.

## 27. NO COMPRIMIR INFORMACIÓN FUNCIONAL

Está prohibido comprimir información funcional explícita del CU en frases genéricas.

NO convertir:
- Una lista de productos en “validar los productos”.
- Una lista de coberturas en “validar las coberturas”.
- Un orden definido en “validar el orden”.
- Una fórmula en “validar el cálculo”.
- Una regla de homologación en “validar homologación”.
- Una condición o excepción en “validar la información”.

Cuando el CU proporcione nombres, listas, orden, valores, criterios, fórmulas o condiciones, conservarlos explícitamente en Description y/o Steps.

## 28. NIVEL DE DESCRIPCIÓN FUNCIONAL

La Description debe permitir que un QA entienda el escenario y las reglas principales sin tener que volver al CU para descubrir qué debe validar.

La Description debe desarrollar, cuando aplique:
1. Ruta funcional integrada al inicio.
2. Objeto funcional a validar.
3. Estructura esperada.
4. Listas y orden.
5. Reglas de negocio.
6. Fuentes de parametrización.
7. Condiciones y excepciones.
8. Cálculos o fórmulas.
9. Resultado funcional esperado.

La profundidad debe ser proporcional a la complejidad del CU: un CU simple no debe hacerse artificialmente extenso, pero un CU con matrices, fórmulas, homologaciones o múltiples reglas debe desarrollarse con el detalle necesario.

## 29. REGLA DE VALIDACIÓN EJECUTABLE

Cada regla funcional relevante debe convertirse en una validación ejecutable.

Una validación ejecutable debe expresar:
ACCIÓN + OBJETO/DATO + CRITERIO + RESULTADO ESPERADO.

Ejemplo insuficiente:
“Validar Pesos Reales.”

Ejemplo correcto:
“Comparar los valores presentados para los productos base en la tabla Pesos Reales contra la parametrización de distribución de pesos de coberturas básicas definida en CU-337.”

Expected:
“Los valores presentados para cada producto y cobertura corresponden a los pesos parametrizados en CU-337.”

## 30. DESCOMPOSICIÓN DE STEPS

Crear Steps suficientes para ejecutar y evidenciar cada comportamiento funcional relevante.

No crear un Step genérico para cubrir varias reglas independientes cuando eso impida comprobarlas individualmente.

Cuando exista una lista extensa, puede validarse en un Step siempre que el Expected conserve explícitamente los elementos y el orden definido.

Cuando exista una fórmula, crear un Step que permita verificar la fórmula y otro, cuando sea necesario, que permita comprobar el resultado.

Cuando exista una homologación, separar como mínimo:
- identificación de la agrupación o condición;
- identificación del elemento homologado;
- validación del resultado asignado.

## 31. MATRIZ INTERNA DE COBERTURA

Antes de finalizar, comprobar internamente que cada elemento relevante del CU tenga cobertura en al menos uno de estos lugares:
- Description.
- Action.
- Expected.
- Precondiciones.
- Resultado esperado.

Si una regla relevante no tiene cobertura, el CP es inválido y debe regenerarse.

## 32. EJEMPLO DE PROFUNDIDAD ESPERADA

Para un CU que defina Pesos Reales, productos, coberturas, parametrización y homologación, NO generar solamente:
“Validar la tabla Pesos Reales y la homologación de productos.”

Debe desarrollarse el comportamiento incluyendo las coberturas, productos, orden, fuente de parametrización, criterio de agrupación, producto base de referencia y resultado de homologación cuando esos elementos estén definidos en la fuente.

Para un CU que defina Pesos Ajustados, debe conservarse la condición de cobertura no incluida, la fórmula de recálculo, las coberturas disponibles y la validación del total del 100 %, cuando estén definidas en la fuente.

## 33. CONTROL DE CALIDAD DE PROFUNDIDAD

Antes de entregar cada CP responder internamente:
- ¿Todas las reglas funcionales explícitas están cubiertas?
- ¿Se conservaron listas importantes?
- ¿Se conservaron órdenes importantes?
- ¿Se conservaron fórmulas?
- ¿Se conservaron condiciones y excepciones?
- ¿Se usaron las fuentes referenciadas?
- ¿Cada comportamiento diferenciado está separado cuando corresponde?
- ¿Los Steps permiten ejecutar la prueba sin interpretar el CU?
- ¿La Description tiene suficiente detalle para comprender el objetivo y las reglas principales?

Si alguna respuesta es NO, regenerar el CP antes de entregarlo.
