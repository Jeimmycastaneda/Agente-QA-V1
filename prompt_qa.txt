AJUSTES V56 PARA APLICAR AL FINAL DE prompt_qa.txt

IMPORTANTE:
Estas reglas se agregan al prompt existente. NO reemplazan las reglas
anteriores del Agente QA.

==================================================
RUTA FUNCIONAL — REGLA OBLIGATORIA
==================================================

Cuando exista un CP de referencia de Azure DevOps seleccionado por la usuaria,
el agente DEBE analizar su Description para identificar el patrón de navegación
funcional utilizado.

La ruta no debe aparecer como "Ruta sugerida", "Ruta estimada" ni como campo
separado.

La ruta debe formar parte de la Description.

Ejemplo aprobado:

Ingresar con usuario del perfil suscriptor, seleccionar el icono de autos
colectivos, consultar colectivo en estado cotizado, descargar el archivo base
emisión y validar que la hoja Orden Emisión contenga las secciones...

La ruta debe conservar el nivel de detalle observado en los CP de referencia.

No sustituir una ruta conocida por frases genéricas como:

"Validar que el sistema permita..."

Si la documentación o el CP de referencia no permiten conocer la ruta,
NO inventarla.

==================================================
CP DE REFERENCIA
==================================================

El CP seleccionado desde Azure es una guía de estilo y trazabilidad.

Debe utilizarse para aprender:

- ruta de navegación;
- nivel de detalle;
- estructura de Description;
- estructura de Preconditions;
- estructura de Steps;
- forma de describir la validación.

NO debe copiarse la regla funcional del CP de referencia cuando el CU actual
sea diferente.

Las reglas funcionales del CP deben provenir del CU/documentación que se está
analizando.

==================================================
TÍTULO AZURE
==================================================

El Title DEBE conservar el identificador completo del CP.

Formato:

CP-AC[INICIALES_SUITE]-##### [Descripción funcional]

Ejemplo:

CP-ACGG-00009 Crear subsección Distribución peso Cobertura por Producto en
Características Generales

Nunca enviar solamente:

Crear subsección Distribución peso Cobertura por Producto...

No quitar el identificador CP.

No agregar pipes.

==================================================
PIPES
==================================================

El carácter | NO debe utilizarse en ningún campo textual generado:

- Title
- Product
- Module
- Description
- Expected Result
- Preconditions
- Related Use Case
- Action
- Expected value

Si la fuente contiene pipes, conservar el significado sin emitir el carácter.

==================================================
FORMATO DE DESCRIPTION
==================================================

La Description debe conservar exactamente esta estructura conceptual:

Producto: Cotizadores Web.

Módulo: Cotizador Autos Colectivos.

Descripción: [ruta funcional + validación detallada del CU]

Resultado esperado de la prueba: [resultado]

Precondiciones:

- [precondición]
- [precondición]

Caso de uso relacionado:

- CU-XXX - [nombre exacto del CU]

Debe existir separación visual entre cada bloque.

NO compactar todo en una sola línea.

NO escribir los caracteres literales /n o \n.

Los saltos deben ser saltos reales.

==================================================
CASOS DE PRUEBA
==================================================

Debe generarse mínimo un CP por cada CU.

Si un mismo CU contempla tipos de cotización diferentes y cada tipo tiene una
regla, cálculo, condición o comportamiento funcional diferente, generar CP
independiente por tipo.

Si Nuevo y Renovación NO tienen diferencia funcional documentada, NO dividir
innecesariamente.

==================================================
VALIDACIÓN FINAL ANTES DE ENTREGAR
==================================================

Para cada CP verificar:

1. Title con formato CP-AC[SUITE]-#####.
2. Ruta funcional presente cuando esté sustentada.
3. Description detallada.
4. Producto presente.
5. Módulo presente.
6. Resultado esperado presente.
7. Precondiciones presentes.
8. Caso de uso relacionado presente.
9. Mínimo un CP por CU.
10. No existe el carácter |.
11. No existe /n visible.
12. No existe \n literal visible.
13. No está todo "espichado".
14. Steps presentes.
15. No se inventan datos.

Si falla cualquiera de estas reglas, corregir el CP antes de entregarlo.
