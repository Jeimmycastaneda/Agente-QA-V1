# PROMPT QA V22 — REFERENCIAS HISTÓRICAS REALMENTE UTILIZABLES

## OBJETIVO
Generar Test Cases funcionales DRAFT usando la HU/documentación actual como fuente de verdad y las referencias históricas cargadas en la aplicación como apoyo para mejorar precisión y nivel de detalle.

La aplicación recupera automáticamente fragmentos históricos relevantes y los entrega al modelo bajo la sección `REFERENCIAS HISTÓRICAS SUGERIDAS`.

## REGLA CRÍTICA DE PRIORIDAD
1. La HU/documentación actual manda.
2. Las referencias históricas NO son hechos confirmados.
3. Una referencia histórica solo puede aparecer como sugerencia.
4. Si una referencia histórica contradice la HU actual, ignorarla.
5. No inventar información.

## FORMATO DE REFERENCIA
Cuando se use una referencia histórica, escribir explícitamente:
`Referencia sugerida: [dato]. Validar contra el ambiente actual.`

## DESCRIPTION
La Description debe:
- explicar contexto funcional;
- identificar la funcionalidad;
- explicar qué se valida;
- aprovechar una referencia histórica relevante cuando exista;
- incorporar la referencia de forma explícita, sin presentarla como confirmada.

Ejemplo de estilo:
`Ingresar al módulo Cotizador Autos Colectivos y acceder a la funcionalidad documentada para validar el comportamiento definido en la HU. Referencia sugerida: documentación histórica ubica esta funcionalidad en [ruta]. Validar contra el ambiente actual.`

## STEPS
Cada acción funcional principal debe ser un Step independiente.

Action y Expected deben estar separados.

Cuando exista una referencia histórica útil:
`Action: Ingresar al módulo... Referencia sugerida: [ruta histórica]. Validar contra el ambiente actual.`

No reemplazar la acción real por la referencia.

## PRECONDICIONES
Usar primero las precondiciones confirmadas por la HU.
Si una referencia histórica aporta una posible precondición no confirmada:
`Referencia sugerida: [precondición]. Validar antes de ejecutar.`

## COBERTURA
- Mínimo 1 CP por cada CU.
- 1 CP = 1 CU.
- No relacionar un CP con varios CU.
- No mezclar funcionalidades.
- Crear escenarios adicionales solo cuando aporten cobertura funcional real y estén sustentados.

## PRODUCTO/MÓDULO
Para Autos Colectivos:
- Producto: `Cotizadores Web`
- Módulo: `Cotizador Autos Colectivos`

## NO INVENCIÓN
Nunca inventar rutas, usuarios, perfiles, permisos, botones, campos, mensajes, URLs, reglas o valores.
Si el histórico aporta un dato potencialmente útil pero no confirmado, marcarlo únicamente como `Referencia sugerida`.

## CALIDAD DE REDACCIÓN
Los casos deben seguir el nivel de detalle de los proyectos históricos:
- Description contextual;
- Expected verificable;
- Preconditions concretas;
- Steps ejecutables;
- Action/Expected separados;
- evitar pasos gigantes;
- evitar resultados genéricos.

## AZURE IMPORT
Mantener el modelo aprobado:
TestCaseId, Title, TestStep, StepAction, StepExpected, TestPointId, Configuration, Tester, Outcome, Comment.

No agregar columnas.
Cada Step ocupa una fila.

Las referencias sugeridas pueden quedar dentro de StepAction/StepExpected y Description se conserva en Datos Adicionales cuando corresponda.

## VALIDACIÓN FINAL
Comprobar:
- todos los CU tienen al menos un CP;
- cada CP tiene un único CU;
- no hay relaciones cruzadas;
- referencias históricas claramente marcadas;
- Description y Steps mejorados cuando exista evidencia;
- sin invención;
- Producto/Módulo correctos;
- Azure Import sin columnas nuevas.
