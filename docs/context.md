# Contexto y objetivo del proyecto

## Objetivo

Agente QA es una herramienta interna para generar casos de prueba QA a partir de Historias de Usuario y documentación funcional, usando un LLM, y exportarlos en formatos listos para Azure DevOps (Excel/PDF). El objetivo de negocio es reducir el tiempo de diseño manual de casos de prueba manteniendo trazabilidad y sin inventar información no presente en la fuente.

Este documento describe el estado actual del proyecto y el estado deseado (roadmap). Se debe mantener actualizado a medida que el proyecto avance: lo que hoy es "deseado" debe pasar a "actual" cuando se implemente.

## Estado actual (bases del proyecto)

- **Modularizado**: `app.py` es solo el entrypoint de Streamlit; la lógica vive en el paquete `agente_qa/` (`config`, `utils`, `extraction`, `prompts`, `providers/gemini`, `generation`, `export/excel`, `export/pdf`, `ui/*`). Ver la sección "Architecture" de `CLAUDE.md` para el detalle módulo por módulo.
- **Interfaz de proveedor de LLM intercambiable (fase 4)**: `agente_qa/providers/base.py` define `LLMProvider` (`Protocol`: `name`, `list_models()`, `default_models()`, `generate(GenerationRequest) -> GenerationResult`), y `agente_qa/providers/__init__.py` expone un registro perezoso (`build_provider(name, api_key)`, `list_providers()`) que importa el módulo del proveedor recién cuando se pide, para que un proveedor futuro con una dependencia faltante no rompa el arranque de la app. `agente_qa/providers/gemini.py` implementa `GeminiProvider` (el único proveedor real hoy — ver la guardia de alcance de la fase 4, no se agregó OpenAI/Anthropic): arma el prompt completo, llama a `google-genai`, parsea el JSON (con fallback a extraer un bloque ```` ```json ```` ```` ```` si hace falta) y clasifica cualquier excepción vía `_classify` (mismos substrings que antes — `"429"/"quota"/"resource exhausted"` → `QuotaError`, `"500"/"internal"/"503"/"unavailable"/"deadline"/"timeout"` → `TransientError`, `"400"/"invalid argument"/"unsupported"` → `BadRequestError`, cualquier otra cosa → `BadRequestError` como fallback que preserva el comportamiento previo de "sin reintento, siguiente modelo"). `agente_qa/generation.py` ya no asume Gemini: `generate_qa_data(prompt, source, provider, model_name, ...)` recibe el `LLMProvider` construido por la UI y solo se ramifica por tipo de excepción tipada (`QuotaError`/`TransientError` reintentan con backoff, `ProviderError`/`ValueError` pasan al siguiente modelo sin reintento).
- **Prompts en Markdown, editables desde la UI**: viven como `.md` en `prompts/` (base: `prompts/qa_base.md`). `agente_qa/prompts.py` expone `list_prompts()`/`load_prompt(name)`/`save_prompt(name, content)`; la sección "📝 Prompt QA" de la app permite elegir el prompt activo (selectbox sobre los `.md` existentes) y editarlo/crear uno nuevo desde un `text_area` básico, sin tocar código. Los nombres se validan (`^[A-Za-z0-9_-]+\.md$`) para que el editor no pueda escribir fuera de `prompts/`.
- **Formatos de export externalizados a YAML**: `AZURE_COLUMNS`/`MATRIZ_COLUMNS`/`EXCEL_CONFIGS` ya no son literales Python: `agente_qa/settings.py` los carga y valida desde `config/columns.yaml` y `config/excel_presets.yaml` (`load_columns`/`load_excel_presets`), con fallback a `agente_qa/defaults.py` si esos archivos faltan. `agente_qa/config.py` sigue exponiendo los mismos nombres públicos (`config.AZURE_COLUMNS`, etc.) derivados del loader, así que `export/excel.py`, `export/pdf.py` y `ui/sidebar.py` no cambiaron. `columns.yaml` es un contrato congelado (`allow_override: false` hard-falla si se modifica); `excel_presets.yaml` admite agregar un nuevo cliente/formato editando solo ese archivo, sin tocar código.
- **Integración directa con Azure DevOps (fase 5, 5a completo + 5b parcial)**: `agente_qa/integrations/azure_devops.py` (`AzureDevOpsClient`) es un cliente REST artesanal sobre `requests` (sin SDK oficial) que crea/actualiza Test Cases vía la API de Work Items, con auth HTTP Basic (usuario vacío, PAT como password) resuelto vía `agente_qa.secrets.resolve_secret(cfg.pat_secret_name)`. **Corrección de alcance importante**: los Test Points *no son creables directamente vía API* — se materializan solo cuando Azure DevOps asocia un Test Case a una Test Suite dentro de un Test Plan. Por eso el trabajo se dividió: **5a** (`create_test_case`/`update_test_case`/`find_test_case_by_title`/`push_test_cases`) crea/actualiza Test Cases con idempotencia (vía `AzureWorkItemId` guardado en el caso + fallback WIQL por título entre sesiones) y dry-run por defecto (`dry_run=True` no hace ninguna llamada de escritura); **5b** (`add_to_test_suite`) asocia un Test Case ya creado a la suite configurada (`test_plan_id`/`test_suite_id`) — es lo único que produce un Test Point real, implementado pero sin UI dedicada todavía. `_steps_to_xml` construye el blob XML de `Microsoft.VSTS.TCM.Steps` (HTML-escapado). Config en `config/azure_devops.yaml`, cargada por `agente_qa.settings.load_azure_devops_config` con dos guardias hard-fail: (1) el YAML nunca puede contener una clave `pat`/`token`/`password` a ninguna profundidad — el PAT vive solo como nombre de secreto (`pat_secret_name`), nunca como valor; (2) `organization_url` debe matchear `^https://(dev\.azure\.com/|[a-z0-9-]+\.visualstudio\.com)` antes de cualquier request, porque el PAT se manda como header `Authorization` a esa URL. `agente_qa/ui/azure_section.py` (`render_azure_section`) solo se renderiza desde `app.py` si `enabled: true` y el PAT resuelve; flujo: probar conexión → vista previa en dry-run (`st.dataframe`) → checkbox "Crear como nuevos (permitir duplicados)" → push real detrás de una confirmación explícita. El export a Excel/PDF (`ui/results.py`) no se modificó — la integración es puramente aditiva. Todo error propagado pasa por `security.redact` antes de mostrarse; 429 se mapea a `TransientError` (reutilizada de `errors.py`) respetando `Retry-After`.
- **Seguridad**: la API key se lee de `st.secrets`/env var (correcto, ahora también disponible vía `agente_qa.secrets.resolve_secret` para reutilizar en fases futuras); ya existe `.gitignore` (excluye `.streamlit/secrets.toml`, `.env`) y `.streamlit/config.toml` limita `maxUploadSize` a 10 MB en el servidor. Los uploads se validan por tamaño/extensión/contenido-real antes de extraerse (`agente_qa/security.py`), y las excepciones tienen una jerarquía tipada (`agente_qa/errors.py`) que separa `user_message` (seguro de mostrar) de `detail` (técnico, solo tras `AGENTE_QA_DEBUG=1`).
- **Streamlit fuera del core**: `generation.py`, `providers/gemini.py` y `prompts.py` ya no importan `streamlit`; solo `agente_qa/ui/*` y `agente_qa/secrets.py` pueden hacerlo. Esto es lo que habilita testear el core en la fase 2.
- **Suite de tests con `pytest`**: `tests/` cubre todo módulo bajo `agente_qa/` salvo `agente_qa/ui/` (golden tests de `export/excel.py` sobre los 3 presets, smoke test de `export/pdf.py`, `utils.py`, `security.py`, `extraction.py`, `prompts.py`, `generation.py` con un `LLMProvider` fake y `time.sleep` inyectado, `errors.py`, `config.py`, `secrets.py`, `providers/gemini.py` — incluida la clasificación de errores de `GeminiProvider._classify` —, `providers/__init__.py`, `settings.py` incluido `load_providers`/`load_default_provider`/`load_azure_devops_config`, `integrations/azure_devops.py` con una sesión HTTP fake inyectada — `_steps_to_xml` contra fixtures de string, JSON-Patch de create/update, WIQL, dry-run sin llamadas de red, 429 → `TransientError`). Sin linter configurado todavía.

- ~~`config.py` sigue teniendo `EXCEL_CONFIGS`/`AZURE_COLUMNS`/`MATRIZ_COLUMNS` como constantes Python — externalizarlas es el punto 6.~~ — hecho (fase 3): ver punto 6.

### 3. Soporte multi-proveedor — ✅ hecho (fase 4)
- ~~Definir una interfaz común (p.ej. `generate(prompt, source, schema) -> dict`) detrás de la cual vivan Gemini, y a futuro otros proveedores (OpenAI, Anthropic, etc.).~~ — hecho: `agente_qa/providers/base.py` (`LLMProvider` Protocol, `GenerationRequest`/`GenerationResult`), registro perezoso en `agente_qa/providers/__init__.py` (`build_provider`/`list_providers`, import por dotted-string vía `importlib` para que una dependencia de proveedor faltante no rompa el arranque), y `GeminiProvider` en `agente_qa/providers/gemini.py` como único proveedor implementado — no se agregó OpenAI/Anthropic reales en esta fase (guardia de alcance explícita).
- ~~La selección de proveedor y modelo debe ser configurable (UI y/o archivo de config), no asumir Gemini en el resto del código.~~ — hecho: `config/providers.yaml` (`default_provider`, `providers.<nombre>.{enabled, secret_name, default_model, max_source_chars, fallback_models}`), cargado y validado por `agente_qa.settings.load_providers()`/`load_default_provider()` con fallback a `agente_qa/defaults.py` si el YAML falta. `agente_qa/generation.py` ya no importa nada de Gemini directamente: `generate_qa_data(prompt, source, provider, model_name, ...)` recibe el `LLMProvider` ya construido. `ui/generation_section.py` lo arma con `providers.build_provider(sidebar_config["provider"], sidebar_config["api_key"])`.
- ~~Mantener la lógica actual de fallback/retry (cuota, errores 5xx, bad request) como comportamiento del proveedor, no de la UI.~~ — hecho: la *clasificación* de errores (substring-sniffing sobre el mensaje del SDK) vive en `GeminiProvider._classify` y devuelve excepciones tipadas (`QuotaError`/`TransientError`/`BadRequestError` de `errors.py`); la *política* de retry/backoff/orden-de-fallback se queda en `generate_qa_data`, que ahora se ramifica por tipo de excepción en vez de por substring.
- Nota de portabilidad: `config.SCHEMA` sigue siendo el JSON Schema canónico, permisivo, con forma de Gemini "por accidente" (solo 5 de 15 propiedades de `TEST_CASES` son `required`) — deliberadamente no se endureció para anticipar un proveedor más estricto (p. ej. OpenAI structured outputs, que exige `additionalProperties: false` y 100% de campos `required`). `GeminiProvider._to_provider_schema` es el punto de extensión reservado para esa adaptación cuando haga falta.

### 4. Prompts editables en Markdown — ✅ hecho (incluye fase 6)
`prompt_qa.txt` se movió (contenido idéntico) a `prompts/qa_base.md`; el selector + editor básico en la UI ya permiten elegir y modificar el prompt activo, y guardar variantes nuevas como otros `.md` en la misma carpeta, sin tocar código. `save_prompt` ya no sobrescribe sin backup: snapshotea el contenido previo con timestamp bajo `prompts/.history/` antes de guardar (`list_prompt_versions`/`read_prompt_version`/`restore_prompt_version`, poda a `MAX_VERSIONS = 20` por prompt vía `_prune_history`); el id de versión se valida por separado (`_VALID_VERSION`) del nombre de prompt (`is_valid_prompt_name`), nunca se concatena crudo en un path. El editor de la UI tiene pestañas "Editar"/"Vista previa" (`st.markdown`, sin `unsafe_allow_html`) y un selector de historial con botón "Restaurar".

### 5. Integración directa con Azure DevOps — ✅ 5a hecho (fase 5), 5b parcial
- ~~Cliente dedicado (`integrations/azure_devops.py`) que use la API REST de Azure DevOps (PAT-based auth) para crear/actualizar Test Cases y Test Points directamente, como alternativa al export Excel manual.~~ — hecho, con una corrección de alcance respecto a la redacción original de este punto: **los Test Points no son creables directamente vía API de Azure DevOps.** Se materializan únicamente cuando un Test Case se asocia a una Test Suite dentro de un Test Plan. La columna `TestPointId` que sintetiza `export/excel.py` (`base_testpoint + idx - 1`) es un artefacto del formato de import Excel, no un id real de Azure DevOps. Por eso el trabajo se dividió: **5a** — crear/actualizar Test Cases (`create_test_case`/`update_test_case`/`find_test_case_by_title`/`push_test_cases`), con dry-run por defecto e idempotencia vía `AzureWorkItemId` + búsqueda WIQL por título — completo. **5b** — asociación a Test Suite (`add_to_test_suite`), que es lo que produce el Test Point real — implementado a nivel de cliente (requiere `test_plan_id`/`test_suite_id` en `config/azure_devops.yaml`), sin botón dedicado todavía en `ui/azure_section.py`.
- ~~El export a Excel debe seguir existiendo como fallback/alternativa, no ser reemplazado.~~ — hecho: `export/excel.py`/`export/pdf.py` y sus botones de descarga en `ui/results.py` no se tocaron; la integración es puramente aditiva.
- ~~Configuración por organización/proyecto de Azure DevOps (URL, proyecto, área, PAT) gestionada igual que las demás credenciales.~~ — hecho: `config/azure_devops.yaml` (`organization_url`, `project`, `area_path`, `iteration_path`, `api_version`, `pat_secret_name`, `test_plan_id`, `test_suite_id`), cargado por `agente_qa.settings.load_azure_devops_config` con guardia anti-secreto-en-YAML y validación estricta de `organization_url` (el riesgo de mayor severidad de todo el roadmap, porque el PAT se envía a esa URL). El PAT en sí se resuelve vía `agente_qa.secrets.resolve_secret(cfg.pat_secret_name)`, igual que `GEMINI_API_KEY`.

### 6. Configuración ampliada y adaptable — ✅ hecho (fase 3)
- ~~Externalizar `EXCEL_CONFIGS`, `AZURE_COLUMNS`, `MATRIZ_COLUMNS` a un archivo de configuración (YAML/JSON) que permita agregar nuevos clientes/formatos sin modificar código.~~ — hecho: `config/columns.yaml` + `config/excel_presets.yaml`, cargados y validados por `agente_qa/settings.py` (`load_columns`, `load_excel_presets`, `ExcelPreset`, `ColumnSpec`), con fallback a `agente_qa/defaults.py` cuando el YAML falta. `agente_qa/config.py` deriva `AZURE_COLUMNS`/`MATRIZ_COLUMNS`/`EXCEL_CONFIGS` del loader sin cambiar sus nombres públicos.
- ~~Los nombres de columna ya aprobados (`AZURE_COLUMNS`) deben mantenerse como el preset por defecto/base al migrar, no renombrarse~~ — hecho: `columns.yaml` trae `allow_override: false` por defecto y el loader lanza `ConfigError` (hard-fail) si `azure_columns` difiere del contrato congelado en `defaults.py`.
- De paso, se corrigió un bug latente en `utils.normalize_case_id`: el regex de preservación de ID hardcodeaba el prefijo `CP-AC-` en vez de usar el parámetro `prefix` recibido, así que un ID generado por el modelo para los presets "Siniestros Fasecolda" (`CP-ACSF-`) o "General QA" (`CP-`) nunca se preservaba. Ahora el regex se parametriza por `prefix`.

## Cómo usar este documento

- Antes de una tarea de arquitectura o de agregar una funcionalidad nueva, revisar qué sección del roadmap aplica y avanzar en esa dirección, respetando la separación por módulo ya existente en `agente_qa/`.
- Al completar un punto del roadmap, actualizar este archivo moviéndolo de "Estado deseado" a "Estado actual".
