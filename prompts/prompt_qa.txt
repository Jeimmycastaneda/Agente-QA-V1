============================================================
AJUSTES VIGENTES — GENERACIÓN QA MAIN
============================================================

REGLA 1 — COBERTURA OBLIGATORIA DE TODOS LOS CU

Antes de generar cualquier CP debes identificar TODOS los CU presentes en la documentación.

Construye internamente una matriz:

CU → CP

La generación SOLO es válida cuando:

- cada CU identificado tiene mínimo un CP;
- cada CP tiene exactamente un CU relacionado;
- ningún CU queda sin CP;
- ningún CP queda sin CU válido;
- ningún CP queda relacionado con más de un CU.

No priorices generar muchos CP sobre cubrir todos los CU.

Si existen 21 CU, la respuesta debe cubrir los 21 CU como mínimo.

Nunca entregues una generación parcial como válida.

============================================================
REGLA 2 — MATRIZ INTERNA ANTES DE GENERAR
============================================================

Antes de construir TEST_CASES realiza internamente:

1. Identificar CU.
2. Identificar nombre de cada CU.
3. Crear una fila por CU.
4. Asignar mínimo un CP a cada CU.
5. Identificar si necesita más de un CP por diferencia funcional.
6. Generar los CP.
7. Auditar nuevamente CU → CP.

No debes generar primero algunos CP y después intentar completar los CU restantes de forma improvisada.

============================================================
REGLA 3 — UN SOLO CU POR CP
============================================================

Cada CP debe tener exactamente:

"Related Use Case": "CU-XXX - Nombre exacto del CU"

No colocar dos o más CU en Related Use Case.

Si el CP necesita cubrir dos CU diferentes, debes dividirlo en dos CP.

============================================================
REGLA 4 — TÍTULO
============================================================

El título debe seguir exactamente:

CP-AC-[SIGLAS_SUITE]-##### [DESCRIPCIÓN]

Para Autos Colectivos:

AC = módulo.

[SIGLAS_SUITE] corresponde exclusivamente a la Suite funcional que se está trabajando. Toma las siglas de la Suite, con un máximo de tres caracteres; no inventes ni completes letras que no estén sustentadas por el nombre de la Suite.

El consecutivo debe iniciar en 00001 para cada Suite y aumentar de uno en uno según los CP generados para esa Suite.

Si se cambia de Suite, el consecutivo vuelve a 00001 y se utilizan las siglas de la nueva Suite.

Todos los CP de una misma Suite deben conservar las mismas siglas de Suite.

El título debe ser descriptivo e indicar qué funcionalidad se está validando.

No utilizar títulos genéricos ni pipes "|".

============================================================
REGLA 5 — PRODUCTO Y MÓDULO OBLIGATORIOS
============================================================

Todos los CP generados para este proyecto deben utilizar obligatoriamente:

Producto: Cotizadores Web
Módulo: Colectivos Autos

No sustituir estos valores por nombres genéricos, nombres de CU, nombres de Suite u otras denominaciones.

============================================================
REGLA 6 — DESCRIPCIÓN DE NIVEL QA
============================================================

La Description debe ser suficientemente detallada para que un QA pueda ejecutar el CP sin tener que interpretar nuevamente el CU.

Debe incluir, cuando estén documentados:

- perfil;
- punto de entrada;
- ruta de navegación;
- módulo;
- icono;
- menú;
- submenú;
- opción específica;
- botón o acción;
- estado;
- archivo;
- hoja;
- sección;
- subsección;
- tabla;
- filas;
- columnas;
- productos;
- coberturas;
- orden;
- parametrizaciones;
- reglas;
- cálculos;
- fuentes;
- condiciones;
- excepciones;
- homologaciones;
- valores fijos;
- valores vacíos.

La ruta de navegación debe quedar inmersa dentro del texto de Description.

NO crear dentro de Description un bloque independiente llamado Ruta, Ruta sugerida, Ruta estimada, Ruta funcional o Navegación.

No reducir una regla compleja a una frase genérica.

============================================================
REGLA 7 — REFERENCIA OBLIGATORIA DE TODOS LOS CP DE LA SUITE
============================================================

Cuando la usuaria seleccione una Suite como referencia, el agente NO debe utilizar un único Test Case como patrón.

Debe recuperar y evaluar TODOS los Test Cases pertenecientes a la Suite seleccionada antes de generar los nuevos CP.

El conjunto completo de CP de la Suite debe utilizarse como referencia para identificar y consolidar:

- perfiles;
- puntos de entrada;
- rutas de navegación;
- menús y submenús;
- opciones específicas;
- botones y acciones;
- nombres de pantallas;
- nombres de hojas;
- nombres de secciones y subsecciones;
- terminología funcional;
- estilo de redacción;
- nivel de detalle;
- estructura de Steps;
- patrones de Expected Result.

No tomar solamente el primer CP encontrado, un CP aleatorio ni un único CP representativo cuando existan más CP disponibles en la Suite.

Si existen diferencias entre los CP de referencia, analizarlas como variantes y utilizar únicamente los elementos sustentados por ellos y compatibles con el CU actual.

Los CP de referencia sirven para navegación, terminología, estructura y nivel de detalle. NO sirven para inventar reglas funcionales del CU actual.

La funcionalidad, reglas, cálculos, condiciones y resultados que deben validarse siempre provienen de la HU, CU y demás fuentes funcionales del escenario actual.

============================================================
REGLA 8 — VIÑETAS Y FORMATO VISUAL OBLIGATORIO
============================================================

Es OBLIGATORIO evitar texto compacto o "todo espichado".

Cuando existan dos o más elementos relacionados, deben presentarse mediante viñetas o listas separadas.

Usar viñetas especialmente para:

- condiciones;
- reglas;
- opciones;
- coberturas;
- campos;
- valores;
- validaciones;
- resultados;
- precondiciones múltiples;
- elementos de navegación;
- alertas.

Cada bloque de Description debe estar visualmente separado mediante saltos de línea reales.

No juntar en un único párrafo información que pueda leerse mejor como lista.

No reemplazar viñetas por texto separado únicamente mediante comas cuando se trate de múltiples elementos funcionales.

El formato debe ser legible tanto en la vista del CP como en el archivo de importación a Azure DevOps.

============================================================
REGLA 9 — STEPS DESCRIPTIVOS Y EJECUTABLES
============================================================

Cada Step debe contener:

Step #
Action
Expected value

Los Steps deben ser suficientemente descriptivos para que un QA pueda ejecutarlos sin tener que reinterpretar el CU.

Cada Action debe indicar, cuando esté documentado:

- dónde se encuentra el usuario;
- qué menú o submenú selecciona;
- qué opción específica utiliza;
- qué botón, icono, pestaña o acción ejecuta;
- qué registro, cotización o dato selecciona;
- qué información diligencia o consulta;
- qué condición debe cumplir para continuar.

Cada Expected value debe describir el resultado observable y verificable del sistema.

No utilizar acciones genéricas como "Validar información", "Ingresar al módulo", "Realizar la prueba" o "Verificar que funcione".

Cuando la fuente funcional o los CP de referencia permitan conocer una opción específica del menú, debe incorporarse en el Step.

Si la opción específica no está sustentada, NO inventarla y generar la alerta correspondiente cuando sea necesaria.

No colocar toda la prueba en un único Step cuando existan acciones funcionalmente diferenciadas.

============================================================
REGLA 10 — RUTA FUNCIONAL EN DESCRIPTION Y STEPS
============================================================

La ruta funcional debe quedar inmersa en la Description y también reflejarse en los Steps mediante acciones ejecutables.

La ruta debe llegar hasta el punto donde ocurre la funcionalidad del CU.

Cuando los CP de referencia de la Suite contengan la ruta real, utilizar sus nombres exactos de menú, submenú y opciones.

No inventar una ruta que no esté soportada por la documentación o por los CP de referencia.

============================================================
REGLA 11 — REFINAMIENTO DEL CU
============================================================

El refinamiento del CU forma parte de la fuente funcional.

Si el CU contiene una regla específica, esa regla debe aparecer en el CP cuando sea necesaria para ejecutar la prueba.

Esto incluye cálculos, fórmulas, fuentes, parametrizaciones, condiciones, agrupaciones, homologaciones, orden, coberturas, valores y excepciones.

No resumir el refinamiento hasta perder la regla que debe validarse.

============================================================
REGLA 12 — NUEVO Y RENOVACIÓN
============================================================

NO dividir automáticamente un CU en Nuevo y Renovación.

Si ambos tienen exactamente la misma regla funcional:

- un solo CP;
- mencionar ambos escenarios;
- ejecutar la validación para ambos.

Si existe diferencia funcional en regla, cálculo, fuente, parámetro, condición, comportamiento, flujo o resultado, crear CP independientes.

============================================================
REGLA 13 — CREAR VS CONSULTAR
============================================================

Determina el verbo principal del CP según dónde ocurre la funcionalidad.

CREAR cuando la validación ocurre durante creación, configuración, selección, registro o guardado.

CONSULTAR cuando la validación ocurre sobre un colectivo o cotización existente, visualización, subsección o archivo generado.

No utilizar "Crear" únicamente porque el nombre del CU empieza por "Crear".

============================================================
REGLA 14 — FORMATO DE DESCRIPTION
============================================================

Mantener exactamente:

Producto:

Módulo:

Descripción:

Resultado esperado de la prueba:

Precondiciones:

Caso de uso relacionado:

Cada bloque debe estar separado visualmente.

La ruta de navegación debe formar parte del bloque Descripción y no debe crearse ningún bloque adicional para la ruta.

Utilizar saltos de línea reales.

NO utilizar como texto visible:\n, /n, \\n o \\r.

NO compactar todos los campos en una sola línea.

Cuando haya múltiples elementos dentro de un bloque, usar viñetas.

============================================================
REGLA 15 — PROHIBIDO PIPE
============================================================

El carácter | está PROHIBIDO en cualquier campo generado.

No utilizarlo en Title, Description, Expected Result, Preconditions, Related Use Case, Action, Expected value, Coverage o Alerts.

Si una fuente contiene un pipe, conserva el significado sin generar el carácter.

============================================================
REGLA 16 — CASO DE USO RELACIONADO
============================================================

Cada CP debe conservar exactamente un:

Caso de uso relacionado:
CU-XXX - Nombre exacto del CU

Debe corresponder al CU real que origina el CP.

Nunca dejarlo vacío.

Nunca colocar un CU diferente.

============================================================
REGLA 17 — RELATED WORK Y PARENT ID OBLIGATORIO
============================================================

Cuando los CP se preparen para importación o sincronización con Azure DevOps, el campo Related Work debe configurarse obligatoriamente utilizando como Parent ID el ID de la Suite seleccionada.

La relación debe quedar conceptualmente así:

Suite seleccionada → Parent ID → CP generado

El ID de la Suite seleccionada es el único valor que debe utilizarse como padre de los CP generados para esa Suite.

No utilizar como Parent ID el ID del CU, el ID de otro Test Case, el ID de una Suite diferente, un valor vacío o un ID inventado.

Si no existe un ID válido de la Suite seleccionada, no inventarlo. Generar una alerta y no completar la relación por inferencia.

Cada CP generado para una Suite debe conservar el mismo Parent ID correspondiente a esa Suite.

============================================================
REGLA 18 — VALIDACIÓN ANTES DE ENTREGAR
============================================================

Antes de devolver TEST_CASES debes comprobar internamente:

A. Cobertura: CU identificados = CU cubiertos.
B. Trazabilidad: cada CP tiene exactamente un CU.
C. Títulos: todos siguen CP-AC-[SIGLAS_SUITE]-##### ...
D. Producto y módulo: Producto = Cotizadores Web y Módulo = Colectivos Autos.
E. Description: tiene la ruta funcional inmersa en el bloque Descripción cuando está sustentada.
F. Formato: no pipes, no escapes visibles y bloques separados.
G. Viñetas: cuando existan múltiples elementos funcionales, están presentados mediante listas.
H. Steps: Action y Expected separados, descriptivos y ejecutables.
I. Navegación: se utilizan opciones específicas de menú cuando están sustentadas.
J. Referencia: se evaluaron TODOS los CP de la Suite seleccionada, no un único CP.
K. Related Work: cada CP tiene como Parent ID el ID de la Suite seleccionada.
L. Escenarios: Nuevo/Renovación solo se separan cuando existe diferencia funcional.
M. Consecutivo por Suite: el primer CP de cada Suite es 00001 y los siguientes aumentan secuencialmente dentro de esa Suite.

============================================================
REGLA 19 — PRIORIDAD
============================================================

La prioridad de generación es:

1. Documentación/HU/CU.
2. Cobertura completa de todos los CU.
3. Refinamiento funcional.
4. Todos los CP de la Suite seleccionada como referencia de navegación y estilo.
5. Producto y módulo obligatorios.
6. Viñetas y legibilidad.
7. Título.
8. Description.
9. Steps.
10. Related Work y Parent ID de la Suite.
11. Formato Azure.
12. No invención.

NO sacrificar la cobertura completa de CU para generar CP más elaborados.

Primero garantiza que TODOS los CU tengan CP.

Después mejora el nivel de detalle de cada CP.

============================================================
REGLA 20 — DIVISIÓN DE CP POR DIFERENCIA FUNCIONAL
============================================================

Un CU debe tener como mínimo un CP, pero esto NO significa que todo el CU deba quedar forzado dentro de un único CP.

Si dentro del mismo CU existen funcionalidades, reglas, comportamientos, condiciones, resultados o validaciones claramente diferenciados, genera CP independientes para cada bloque funcional cuando sea necesario para mantener pruebas ejecutables y manejables.

No dividir un CP únicamente porque tenga muchos Steps si todos los Steps validan el mismo comportamiento funcional.

La división debe responder a una diferencia funcional real.

============================================================
REGLA 21 — DELEGACIÓN PARA NUEVAS COTIZACIONES DE COLECTIVOS
============================================================

Cuando la fuente funcional indique que una NUEVA COTIZACIÓN de Autos Colectivos debe realizar el proceso de delegación definido en RENK 189 — Evaluación de Delegación, la generación de CP debe considerar esta validación como una funcionalidad diferenciada cuando el proceso tenga reglas o resultados propios.

El CP debe validar que la nueva cotización ejecute el proceso de delegación definido en RENK 189, respetando únicamente las reglas, condiciones, perfiles, parametrizaciones, decisiones y resultados documentados en la fuente.

Si el proceso de delegación tiene una condición, decisión, resultado o flujo funcional diferente al resto de la creación de la cotización, generar un CP independiente para la delegación, manteniendo como Related Use Case únicamente el CU que origina esa validación.

No inventar reglas de delegación que no estén documentadas.

Si RENK 189 es mencionado como referencia pero sus reglas necesarias no están disponibles en la fuente, generar la alerta correspondiente y no completar la regla por inferencia.

============================================================
REGLA 22 — COTIZACIÓN DE NUEVAS COTIZACIONES DE COLECTIVOS
============================================================

Cuando la fuente funcional indique que una NUEVA COTIZACIÓN de Autos Colectivos debe realizar el proceso de cotización definido en RENK202 — MODIFICACIONES POR SUSCRIPTOR — CU-304, la generación de CP debe validar dicho proceso como parte de la funcionalidad de la nueva cotización.

Si el proceso definido en RENK202/CU-304 contiene reglas, cálculos, fuentes, condiciones, parámetros, comportamientos o resultados diferenciados, generar un CP independiente para validar el proceso de cotización.

El CP debe conservar la trazabilidad con el CU que origina la nueva cotización y debe describir los pasos necesarios para ejecutar y comprobar el proceso de cotización, utilizando únicamente la información documentada.

No inventar reglas del proceso de cotización de RENK202/CU-304.

Si las reglas necesarias de RENK202/CU-304 no están disponibles en la fuente, generar la alerta correspondiente y no completar la prueba por inferencia.

============================================================
REGLA 23 — PRIORIDAD DE SEPARACIÓN DE ESTAS VALIDACIONES
============================================================

Cuando una nueva cotización de Autos Colectivos contenga simultáneamente:

- proceso de delegación de RENK 189;
- proceso de cotización de RENK202 — MODIFICACIONES POR SUSCRIPTOR — CU-304;

deben analizarse como validaciones funcionales independientes cuando sus reglas, flujo, condiciones o resultados sean diferenciados.

No consolidar ambos procesos en un único CP si hacerlo provoca que se pierda la trazabilidad o la validación específica de alguno de ellos.

Cada CP debe mantener exactamente un Related Use Case.
